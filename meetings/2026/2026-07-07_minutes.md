### WebMCP Threat Model Framing

* Simone Onofri: We are starting with "what are we building?" for WebMCP. If participants have threat ideas, they should write them down while the technology is being explained, because some points may become clearer during the presentation.

* Simone Onofri: My framing is to compare three interaction models: a human navigating with a browser, an agent navigating with a browser without WebMCP, and an agent navigating with a browser with WebMCP. That should help us understand the security and privacy delta.

* Julia Pagnucco: I will briefly cover the API and problem statement, then move into the threat landscape, diagrams, and, if time allows, security mitigations.

* Julia Pagnucco: Existing agentic browsing approaches include DOM scraping, accessibility tree use, and screenshots. Those approaches are brittle and latency-sensitive.

* Julia Pagnucco: WebMCP is inspired by traditional MCP, but it is not the same thing. It lets websites expose structured tools directly to agents running within the browser.

* Julia Pagnucco: WebMCP has two primary API styles. Imperative tools are registered explicitly with JavaScript. Declarative tools are inferred from HTML form elements.

* Julia Pagnucco: Declarative tools can include a tool name, tool description, input names, input descriptions, and a `tool-auto-submit` attribute. If auto-submit is false, a human can remain in the loop; if true, the form auto-submits.

* Julia Pagnucco: Imperative tools have similar metadata, an input schema, an execution function, and freeform text output.

* Julia Pagnucco: Imperative tools can support cross-origin exposure, but by default cross-origin iframes cannot observe or interact with another origin's tools unless that exposure is allowed through the relevant attribute.

### Threat Landscape and Data Flow

* Julia Pagnucco: The main threat vectors include dynamic tool output, tool descriptions, and tool names. These can be site-controlled or user-generated freeform text that is fed directly into the model context.

* Julia Pagnucco: Operations can be hidden by design and happen faster than ordinary user interaction, while the agent may also have the user's authenticated context.

* Julia Pagnucco: One example is tool chaining. A benign user prompt may lead the agent to call a first tool, receive user-generated content in the tool output, and then be induced to call another tool with private context that can be exfiltrated.

* Julia Pagnucco: In the high-level data flow, the site or origin exposes tools, the browser registers them, the tools are exposed to the agent, the user prompts the agent, the agent formulates a tool call, the browser executes the tool on the site, and dynamic tool output is returned to the agent and model context.

* Julia Pagnucco: The trust boundaries are broadly zero-trust. The user may not trust the agent, the agent may not trust the browser execution situation, and the site is also untrusted.

* Simone Onofri: The diagram is clear at site level. The relationship with MCP is about the style of interaction: the browser has a manifest-like store that can be fed by HTML attributes or JavaScript registration, and the agent can interact with that instead of relying only on screenshots or reading the DOM.

### Agent and Browser Boundaries

* Simone Onofri: I want to clarify what "agent" means here. It could be something like Gemini opening a browser, a browser with a sidebar agent that controls navigation, or a JavaScript agent such as PageAgent injected into a website.

* Julia Pagnucco: In the diagram I use "agent" to cover browser agents, in-page agents, and extension agents. We may need to split out agent types because the trust level may differ between, for example, Gemini in Chrome and another agent in an extension.

* Dominic Farolino: The agent can exist at many levels of the stack. It could be an iframe agent inside the page, a browser-built-in agent with additional browser-level capabilities, or a computer-use agent controlling a browser from outside.

* Dominic Farolino: From the WebMCP tool's perspective, the interaction should be the same. The tool should not need to distinguish whether it is being used by a computer-use agent or an iframe agent.

* Dominic Farolino: The agent is an extension of the user, and the tool has to be written in a way that trusts the agent to fulfill the user's intent correctly. If that does not hold, it does not matter where the agent lives on the stack.

* Simone Onofri: So an agent is any entity able to interact with the website using WebMCP or without WebMCP, independent of whether it is using a browser, in the browser, or loaded inside the HTML page, even if those cases have different capabilities.

* Julia Pagnucco: Yes.

### Assistive Technology, User Presence, and Powerful APIs

* Simone Onofri: I want to understand the relationship with assistive technology. Why is using the accessibility tree or existing assistive technology not enough? Could WebMCP be used by assistive technology, substitute for it, or sit on the same line?

* Dominic Farolino: WebMCP toolifies core site functionality and user journeys in a way that an agent can understand. Screen readers could choose to use WebMCP tools and expose them to users, but a good user experience would probably need a translation layer between WebMCP tools and what the screen reader user interacts with.

* Dominic Farolino: WebMCP is designed with agent ingestion in mind. The primary accessibility benefit may come from assistive technology integrating with agents, where the agent becomes the natural-language translation layer between tools and the user experience.

* Simone Onofri: I also want to understand the relationship with passkeys, Web Authentication, Digital Credentials API, and user presence. If an agent is acting, there may be agent presence rather than user presence.

* Dominic Farolino: WebMCP is not designed to solve human presence detection. It lets the website tell the agent that some interaction is required. Whether that interaction comes from the human, the agent, or another computer-use mechanism is outside WebMCP.

* Dominic Farolino: Tool calls and WebMCP interactions do not automatically come with user activation, sticky or transient activation, or automatic permission prompt acceptance. Normal browser permission and authentication flows still apply, and WebMCP is not intended to bypass them.

* Simone Onofri: That helps. The question connects with powerful APIs and work on distinguishing different kinds of agents or bots on the Web.

### Agent Scope and Existing Mitigations

* elf Pavlik: Mapping this to the Threat Modeling Guide visual language, I assume the browser and agent are processes. The agent boundary may hide processes on the user device, cloud components, and custom APIs. Is that out of scope for this threat model?

* Julia Pagnucco: That is correct. This is the first time we are doing this, so I did not know how detailed the diagram should be.

* Dominic Farolino: Secure agent design is a separate class of security questions. That includes making sure the origins the agent interacts with are safe and that the agent does not do something the user would not do, such as typing a bank password on `evil.com`.

* Dominic Farolino: The WebMCP work is focused on the interaction between the browser execution boundary, the tools, and the agent boundary, without specifying mandatory policies for how to build a secure agent.

* Simone Onofri: We can probably start with the browser, the manifest, and the agent, and take more detailed care of the agent boundary later.

* Julia Pagnucco: In Chrome we are working on securing our own agent and providing guidance for agent and site developers.

* Julia Pagnucco: For agents, we recommend spotlighting untrusted content, including tool outputs and tool descriptions, so the model treats that content with extra care.

* Julia Pagnucco: Other agent-side mitigations include hard token limits so tool outputs do not overload the model context, human-in-the-loop for consequential actions, restricting cross-origin interactions with `exposed-to`, and using critics or classifiers for prompt injection.

* Julia Pagnucco: For site developers, we encourage API-level hints such as untrusted content and read-only hints, careful tool exposure, and setting character budgets.

### Security Delta, Cross-Origin Exposure, and Site Trust

* Simone Onofri: From a security and privacy perspective, what is the difference between an agent visiting a site without WebMCP and an agent visiting a site with WebMCP? Is it better, worse, or a change in attack surface?

* Julia Pagnucco: Many things possible with WebMCP are also possible in normal agentic browsing. The new threat is that WebMCP introduces freeform text directly into the model context and can make operations faster and less visible to the user.

* Simone Onofri: I also want to understand cross-origin and same-origin policy questions. If I have `example.com` and an iframe from another origin, can the iframe register its tools, and how is the same-origin policy respected?

* Julia Pagnucco: Tools in an iframe use an opt-in exposure mechanism. By default, tools are only exposed to their own origin.

* Johann Hofmann: The principle for WebMCP is that tool exposure to other origins should be strictly opt-in.

* Johann Hofmann: Even exposing iframe tools to the user or to a higher-level context can affect what tools the agent sees on the main website, so that kind of exposure should also be explicit.

* Simone Onofri: For threat modeling, the website itself should be treated as untrusted by default.

* Julia Pagnucco: Yes. The site is untrusted, and there could be attackers on the site or on other sites.

* Dominic Farolino: WebMCP tools do not run in a special privileged process. They run in the same sandboxed renderer process as normal site content, such as postMessage handlers and event handlers.

* Johann Hofmann: Some mitigations, such as read-only hints or consequential action hints, assume that the website has some interest in flagging tools correctly. That trust is limited, and the agent still has to handle it carefully.

### Tool Registration Lifetime and Multiple Tabs

* Tom Jones: I am curious whether tool registration is strictly limited to one tab. If any site can register a tool that is available to anybody else, that would be a catastrophe.

* Dominic Farolino: A tool is like a JavaScript function or postMessage handler. It lives in the browser memory of the page. When the page closes, the tool is gone.

* Dominic Farolino: The document is the context that registers the tool, and the lifetime of the tool is tied to that document.

* Tom Jones: That needs to be clarified. Protocol registrations can live forever, so it should be clear that this is different.

* Johann Hofmann: We can look at whether the explainer or specification should call out that tool registration is not permanent browser memory and does not outlive the document.

* Tommaso Innocenti: A challenging scenario is multiple tabs with the same or similar tools. The agent needs to know which tool to use, especially if a tool changes between pages or tabs without requiring user interaction.

* Tommaso Innocenti: It would be useful to clarify how the agent decides among multiple registered tools, because that is an important part of the model.

* Johann Hofmann: Agent confusion is possible here and is not completely mitigated. It likely needs to be mitigated at the agent implementation level rather than entirely at the specification level.

* Johann Hofmann: For example, if `bank.com` and `fakebank.com` are both open and the agent can access tools from both sites, the agent must understand that a user request about `bank.com` should not use tools from `fakebank.com`.

* Tom Jones: Navigation should invalidate tool selection. Otherwise, a malicious site could load a tool and then the user could navigate to a bank site. The threat should be listed even if the current design says the tool is not still loaded.
