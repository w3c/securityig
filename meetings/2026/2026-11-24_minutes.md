## Notes

### Verifiable Credential Barcodes Review

The discussion concerned [Verifiable Credential Barcodes v1.0](https://github.com/w3c/security-request/issues/143).

* Yuqing Yang: The proposal adds verifiable credential information and a signature to machine readable barcodes. I have three review points. First, the proof configuration appears to raise an error only when both the proof type and cryptosuite are wrong; I think either invalid value should be enough. Second, the specification should explain what happens when a verifier cannot connect to check a credential, including whether verification fails or falls back to a less secure mode. Third, a person using the scanner may need to know whether the data came from a signed barcode or an older unsigned one.

* Simone Onofri: Which points need to be addressed before the specification advances to Candidate Recommendation, and which could be addressed before it exits Candidate Recommendation? We can also suggest guidance in Security Considerations for implementers who need to notify users about verification results.

* Yuqing Yang: I would prioritize clarifying the proof configuration and the behavior when connectivity is lost before the next stage. User notification for signed versus older barcodes would be useful, but could be guidance rather than a requirement of this protocol.

* elf Pavlik: I would like to understand the conformance classes and which implementations the specification covers. Are we discussing barcode parsers and serializers, or an extension of existing verifiable credential processing?

* Yuqing Yang: The proposal adds fields to the data structure and uses existing barcode encoding and compression techniques. It carries verifiable credential and data integrity proof information in a PDF417 barcode or another supported code format. I think it inherits some of the existing verifiable credential model, but the precise implementation boundary needs to be clear.

* Simone Onofri: A verifiable barcode may be printed on a physical card, but QR codes can also be generated by applications and change frequently. We should check whether those different use cases affect the review.

* Yuqing Yang: Static printed credentials, such as driving licences and permits, need particular attention. The proposal is not tied to one code format, but its verification behavior needs to work for a static code and make a failed verification understandable. Dynamic payment QR codes often use short lived tokens instead of putting signed identity data in the code, so I would treat those as a different use case.

* Tom Jones: The example in the specification seems focused on North American driving licences. How does this work fit W3C's international scope?

* Yuqing Yang: The example is North American, but printed permits and digital driving licences with QR codes are also used elsewhere. I have seen examples in China and Macau, though their mechanisms differ.

* Simone Onofri: I may ask W3C China whether people working on Alipay or WeChat payment codes could offer relevant experience. Their use of QR codes is different, so that input would help clarify the boundary rather than make the cases identical.

* elf Pavlik: The design goals mention real time status without phoning home. How is revocation checked without disclosing each verification to the issuer? I would also like to understand how the W3C status list work relates to the IETF draft we mentioned.

* Tom Jones: A status check that phones home raises a privacy problem. I am concerned about whether real time revocation can avoid it.

* Joe Andrieu: A status list can cover many credentials at once, so a request for the list need not reveal which credential is being checked. That is its intended privacy property. A credential could still carry a uniquely identifying status URL in a nonconformant implementation, which would recreate a phone home risk. The holder fetching and presenting the list is another possible approach. I see status checks as a dependency concern for the barcode specification, distinct from its data integrity mechanism. I do not know how the W3C and IETF drafts relate.

* Tom Jones: I oppose this barcode work being within W3C's scope. The example contains personal information, and I think other approaches to signed physical credentials should be considered. I will send a link to a related smart card example.

* Joe Andrieu: I see a W3C role because QR codes already connect physical spaces and web interactions. The barcode work provides a way to sign a statement, check that its issuer is recognized, and check its status. Whether a particular barcode contains personal information is a separate policy and deployment question. I think these integrity and revocation properties can improve physical credentials.

* Simone Onofri: I share concerns about codes that people cannot read directly, while QR codes are already used as links on the web. A separate SING deliverable could map threats and possible mitigations for QR codes used on the web, perhaps with TAG involvement. One idea is for a browser to expose the underlying link when a page presents it as a QR code. This is a topic for interested contributors, not a decision to start a deliverable today.

* elf Pavlik: I would like to revisit the specification with a diagram of the parties, processes, and information flows. That would help show what is in scope and where verification results should be shown to users.

* Yuqing Yang: A threat model should identify the possible attackers and affected people. We need to be clear about who the “user” is in each scenario.

* Simone Onofri: I would start with the actors and data flows, then consider how each actor might be adversarial: a holder might present false information, a verifier might misuse data, and an observer might scan a code. The Threat Modeling Guide has stakeholder examples that could help.

* Tom Jones: I am concerned that a party could create a code or verification service that falsely reports a credential as valid. Recognizing authorities across jurisdictions is also difficult.

* Joe Andrieu: The signature only helps when the verifier has a trustworthy way to identify the issuer's public key. A code that simply points to an arbitrary website does not provide that assurance. Building and maintaining the set of recognized authorities is a real deployment problem, and the relevant set depends on the verifier's jurisdiction and purpose.

* Cosmin Truta: How many issuer authorities and keys would a verifier need to recognize, how often would that information change, and could the verifier update a local list without contacting an issuer for each barcode check?

* Joe Andrieu: The answer depends on the credential and jurisdiction. The lifetime of an issuing agency and the lifetime of its cryptographic keys are different. Whether a periodically updated list works depends on its update and status mechanisms.

* Simone Onofri: We can coordinate with Yuqing by email to turn the review comments into issues. I may also file an issue about a broken threat model link in the specification.
