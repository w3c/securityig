### WebMCP Threat Model Status and Scope

* Simone Onofri: The current WebMCP threat model consolidates notes from previous SING and Threat Modeling Community Group discussions. It also includes work by Zara, particularly on diagrams, which still needs to be reconciled with the main draft.

* Simone Onofri: The analysis starts from the WebMCP specification and uses Blink and Chromium source code where the specification is incomplete or where implementation details help explain the system.

* Simone Onofri: A new tool-execution algorithm was added to the specification shortly before this meeting, so that part of the model still needs to be integrated.

* Simone Onofri: The document is a very early working draft. The plan is to discuss it with the group, publish it on GitHub, convert the current Markdown to Bikeshed, and experiment with Joe Andrieu's threat-model tooling.

* Simone Onofri: The WebMCP material identifies browser-integrated agents and in-page agents as two main cases. An open question for the WebMCP editors is whether ordinary agentic navigation from outside the browser is also an intended use case.

* Simone Onofri: The current inventory contains approximately 26 threats collected from prior discussions and analysis. In my interpretation, only about half are directly attributable to WebMCP; many others arise from agentic navigation or MCP-style interaction more generally.

* Simone Onofri: Nishant Jain shared a proof of concept involving prompt injection through WebMCP. Prompt injection is important to the model, but it is not necessarily specific to WebMCP.

* Simone Onofri: The model uses the W3C Threat Modeling Guide. The Web threat model also provides a reusable baseline that can be specialized for WebMCP.

* Simone Onofri: The high-level diagram includes the user, an AI agent orchestrator, the browser and its isolated page context, the website, and an AI inference provider. The inference provider is shown as external, but it could also run locally.

* Simone Onofri: The diagram also represents the WebMCP tool store and pending tool executions. It traces flows for tool registration and invocation across browser and page trust boundaries.

* Simone Onofri: The terminology is partly derived from the specification, while labels such as “AI agent orchestrator” and “AI inference provider” are modeling terms added to distinguish roles that the specification does not yet define as conformance classes.

* Simone Onofri: The pending tool executions map is represented from the specification. The declarative tool-registration path is not yet fully defined in the specification, although it is described in the explainer and represented in Chromium source code.

* Simone Onofri: The current model prioritizes the specification and then consults implementation code where necessary. Each model element and data flow records its source so that the coverage of the model can be assessed.

* elf Pavlik: The revised diagram is clearer than the earlier versions. Separating the agent orchestrator from the inference provider is useful, and the amount of detail is appropriate.

* elf Pavlik: The baseline Web elements should remain in the diagram. Color could distinguish elements inherited from the general Web threat model from those introduced for WebMCP.

* Joe Andrieu: I support using color. The diagram has enough detail while still fitting on one screen, but processes should have more visibly rounded corners so that they are distinguishable from external entities.

* Gabriel Corona: The agent orchestrator may have access to tools outside WebMCP, such as local filesystem tools or other MCP and native capabilities. Those tools should appear in the model because they create additional threat vectors.

* Simone Onofri: The feedback suggests reconsidering some trust boundaries, especially when the agent runs inside the browser, and possibly removing the outer boundary around entities that are already modeled as external.

* Simone Onofri: A lower-level diagram focuses on WebMCP methods derived from the WebIDL. A still more detailed level could show individual specification algorithms, but including every level in the main document may make the model harder to use.

* Simone Onofri: The dictionaries are organized by element type and include sources, trust boundaries, and data flows. This is intended to preserve traceability and make gaps in the model visible.

* Simone Onofri: The threat table includes an applicability field intended to distinguish threats introduced by WebMCP from threats that would remain in ordinary agentic browsing without WebMCP.

* Simone Onofri: Prompt injection can originate in tool names, descriptions, and untrusted tool output. The WebMCP material already discusses some mitigations, including limits on label size, but the mapping between each threat and its response still needs work.

* Simone Onofri: Other threats include differences between what a human-facing interface appears to do and what an agent-facing tool actually does, unintended consequential actions, and over-parameterization that may let a site request more agent context than it needs.

* Simone Onofri: The next phase is to develop the response analysis, map threats to specification text, and decide whether selected algorithms need a deeper model.

* elf Pavlik: The model currently links to specification sections that provide context, but it should also link threats and mitigations to precise definitions, normative statements, and Security Considerations text.

* Simone Onofri: The Digital Credentials API work provides one possible pattern. Its Security Considerations can name a threat, explain the specification response, link to the relevant normative requirement, and identify residual risk.

* Simone Onofri: For example, a threat involving network manipulation can be connected to a Secure Contexts requirement, while the remaining risk from an attacker inside the browser boundary can be documented separately.

* elf Pavlik: I will open an issue proposing a future Threat Modeling Community Group session on linking threat models, specification requirements, mitigations, and residual risks.

* Tom Jones: My main concern is whether WebMCP can create a service with access to capabilities that ordinary page JavaScript or the DOM would not normally have. I am not sure how to determine whether WebMCP enables that case.

* Simone Onofri: My current interpretation is that WebMCP exposes existing website functionality in a structured tool form so that an agent can use it more reliably. It does not itself add new website functionality, but this should be confirmed with the WebMCP editors and through implementation testing.

* Simone Onofri: One simple analogy is search-engine optimization for agentic browsers: the site describes how an agent should interact with existing functionality instead of requiring repeated screenshots, DOM inspection, or accessibility-tree interpretation.

* Joe Andrieu: WebMCP lets a website expose interfaces that an agent in the browser can use; it is not primarily a way for the website to gain new access to browser services.

* Joe Andrieu: A related concern remains valid because the website and agent can create a bidirectional data flow. Tool output may influence the agent to reveal more information to the site, including through prompt injection.

* Tom Jones: Even if that concern is not unique to WebMCP, WebMCP may make data exfiltration easier. The model should examine that security delta explicitly.

* Simone Onofri: Nishant Jain and the WebMCP editors are appropriate people to ask about the implementation boundary and whether the tools can reach capabilities beyond the page's ordinary authority.

### Voice AI Threat Model

* Tom Jones: I added a voice AI threat model that began in another group and is now available in the repository. It is not yet specifically a W3C problem, but it may become relevant as voice interaction becomes more important.

* Tom Jones: The document includes references to academic work on voice, AI, and browsers. I am looking for contributors and comments on the model.

* Joe Andrieu: The model would benefit from a diagram. Without one, it is unclear which people, devices, agents, and observers are inside the system and where information can flow.

* Joe Andrieu: Voice interaction occurs in an analog environment where nearby people may hear sensitive information. A pharmacy counter is a useful example because spoken exchanges can reveal medication, age, phone numbers, and other personal information to bystanders.

* Joe Andrieu: The model should distinguish the privacy of the person intentionally speaking to the agent from bystander privacy. Background voices and environmental sounds may also be captured by microphones even when those people are not interacting with the system.

* Tom Jones: The pharmacy scenario is a useful use case, and I will consider adding use cases to the model.

* Simone Onofri: Voice assistants also create spoofing and unintended-activation scenarios. A child, a recording, media content, or a remote sound source may cause an assistant to execute an action without the intended user's instruction.

* Simone Onofri: Voice dictation is another basic use case. Even without deepfakes, a system may collect voice data or accept speech that does not come from the person it assumes is speaking.

* Simone Onofri: I will check whether earlier W3C work on voice agents is still active or provides reusable material for this threat model.
